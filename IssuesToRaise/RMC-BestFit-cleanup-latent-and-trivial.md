# Small fixes in RMC.BestFit.App: latent null dereferences, an unthemed progress bar and stale code

**Target:** [USACE-RMC/RMC-BestFit](https://github.com/USACE-RMC/RMC-BestFit), `src/RMC.BestFit.App` (`MarkovChainTraceControl`, `QuantilePriorsControl`, `MainProjectNode`, `BatchRunWindow`, `TimeSeriesControl`, `BivariateAnalysisControl`, `BivariateAnalysisPropertiesControl`, `CompositeAnalysisPropertiesControl`, `CoincidentFrequencyPropertiesControl`, `RatingCurveAnalysisPropertiesControl`). Found in 2.0.1 at commit [`bfce2dd`](https://github.com/USACE-RMC/RMC-BestFit/tree/bfce2ddbebb8d75e6cf6e21c4fef8ecfb5058269), still `main` on 2026-10-31.

**Type:** bug (cleanup) · **Severity:** low

**Verification:** verified by reading the source; none of these was run. Items 1, 3 and 7 are latent: no current path I found triggers them.

## Summary

A checklist of small problems found while porting the application's views. None changes results today; each is a one- or two-line fix. A related item, the unused `BestFitStyles.xaml`, is filed separately in [`RMC-BestFit-unused-bestfitstyles-dictionary.md`](RMC-BestFit-unused-bestfitstyles-dictionary.md).

## Details and how to reproduce

1. **The trace plot reads `Results.MarkovChains` without a null check.** `MarkovChainTraceControl`'s update path guards `Analysis`, `IsEstimated` and `Results`, then calls `Analysis.Results.MarkovChains.Count()`. `MCMCResults.MarkovChains` is declared nullable and is left null by the constructor that takes a MAP and a list of parameter sets, which `Bulletin17CAnalysis` uses. The cache builder in the same control does check for null. The Bulletin 17C view doesn't host the trace control, so this can't happen today, but any future analysis that builds its results that way and shows a trace would throw.
2. **`QuantilePriorsControl` binds a check box's `Visibility` two-way.** The source is the control's own `ShowSingleQuantileCheckBox` property, and nothing else sets the check box's visibility, so `Mode=TwoWay` serves no purpose and invites a write-back if anything ever does.
3. **`GetPropertiesControl` calls `_plotPropertiesControl.Plot.Equals(plot)` without checking `Plot` for null** in 11 of its 12 branches. The twelfth, and `PlotPropertiesCalled`, check it, the latter with the comment "if `_plotPropertiesOpen` was set true but `_plotPropertiesControl.Plot` was reset to null by a separate code path, dereferencing `.Plot.Equals` would NRE". The same reasoning applies to the 11 unguarded branches.
4. **The batch run window's progress bars lose the theme's style.** Each progress bar has a local `Style` (for its visibility triggers) without `BasedOn`. A local style replaces the implicit `ProgressBar` style that the Themes library merges into the application, so these bars use WPF's default template rather than the theme's. The window's local `TextBlock` and `Image` styles don't lose anything, since the Themes library defines no implicit style for those types. Its `DataGrid.RowStyle` does replace the theme's `DataGridRowStyle`, which the theme's `DataGrid` style sets ([`DataGrid.xaml` line 354](https://github.com/USACE-RMC/WPF-Framework/blob/7f897e107db4a25cca29127ce9d564898c5fde93/src/Themes/Resources/Controls/DataGrid.xaml#L354)); it sets its own theme colours, so that may be deliberate.
5. **The batch run window declares a `BooleanToVisibilityConverter` (`BoolToVisConverter`) that nothing uses.**
6. **`DocumentClosed`'s documentation says it saves plot settings.** The summary says it "Saves plot settings to the element", and the remarks list "Serializes and saves all plot configurations back to the element". The method only unsubscribes events (and clears one view's element); a comment inside it says plots are owned by the element, so no serialisation is needed on close. The documentation should match.
7. **Setting `Element` on a Time Series view that's already shown leaves it stale.** The `Element` callback sets `_isLoaded = false` so that "the next Loaded event re-initializes plots for the new element", and the view's update handlers do nothing while `_isLoaded` is false. A view that's already loaded gets no further `Loaded` event, so it would stop updating. The shell creates a new view per element, so this doesn't happen today.
8. **The Bivariate properties panel has unused members:** a `CredibleIntervalItems` collection that nothing binds, and two handlers, `CredibleInterval_PreviewMouseLeftButtonDown` and `OutputLength_PreviewMouseLeftButtonDown`, that nothing wires up.
9. **Its `CopulaComboBox_SelectionChanged` handler is empty,** though the XAML wires it.
10. **Its progress reporter is named `nameof(UnivariateAnalysis)`,** copied from the univariate panel. The Rating Curve, Time Series Analysis, Composite, Mixture and Point Process panels have the same copy. Nothing in RMC-BestFit or WPF-Framework reads `SafeProgressReporter.TaskName`, so it's only misleading.
11. **The Bivariate view checks for a "Minimum" row that its summary table never has.** `SummaryStatisticsTable_LoadingRow` draws a separator above "Minimum" or "AIC", but the table holds the parameters, then AIC, BIC, DIC, WAIC, LOO-CV and RMSE.
12. **The Composite panel's Point Estimator binds its width to an element that doesn't exist.** Its `PropertyWidth` binds to `ElementName=CredibleIntervalWidthComboBox`; the panel has no element of that name, so the binding fails (logged) and the field keeps its default width. The Coincident Frequency panel's Point Estimator binds to `CredibleInterval`, the field above it.
13. **The Coincident Frequency panel has a `BayesianOutputControl_ShowPropertyAttributes` handler for a control it doesn't have.** Five other panels host a `BayesianOutputControl` and wire this handler to it; this panel has its own credible-interval and point-estimator fields instead, and nothing calls the handler.
14. **The Rating Curve panel has two handlers wired to nothing:** `CredibleInterval_PreviewMouseLeftButtonDown` and `OutputLength_PreviewMouseLeftButtonDown`. Its credible interval and output length are in its `BayesianOutputControl`, which shows their attributes through `ShowPropertyAttributes`.

## Why this is an issue and not intended behaviour

Items 1 and 3 are guards the code already applies elsewhere for the same values; item 3's own comment says the value can be null. Item 4 is the usual WPF trap of a local style without `BasedOn`, and the result differs from every other progress bar in the application. Items 2, 5 and 6 are leftovers that mislead readers, as are items 8 to 11, 13 and 14. Item 12 names an element that no file in the application defines; the Coincident Frequency panel shows what was meant. Item 7's own comment shows the intent: re-initialise for the new element, which only works if a `Loaded` event follows.

## Suggested fix

1. `if (Analysis.Results.MarkovChains == null || Analysis.NumberOfChains != Analysis.Results.MarkovChains.Length)`, treating null like the cache builder does.
2. Drop `Mode=TwoWay` (and `UpdateSourceTrigger`).
3. Add `_plotPropertiesControl.Plot != null &&` to the 11 conditions, or compare with `Equals(_plotPropertiesControl.Plot, plot)`, or factor the check into one helper.
4. Add `BasedOn="{StaticResource {x:Type ProgressBar}}"` to the progress bar's style.
5. Delete the converter.
6. Reword the summary to say the method unsubscribes the views' events, and drop the serialisation item.
7. If the view is already loaded when `Element` changes, re-initialise it at once instead of waiting for `Loaded`.
8. Delete the collection and the two handlers.
9. Delete the handler and its `SelectionChanged` attribute.
10. Use each analysis's own name (`nameof(BivariateAnalysis)` and so on).
11. Check for "AIC" only.
12. Bind to `CredibleInterval`, as the Coincident Frequency panel does.
13. Delete the handler.
14. Delete the two handlers.

No compatibility risk.
